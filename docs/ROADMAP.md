# 离「完善」还差什么

> 2026-11-20 状态：本页是优先级和发布门槛，不承担源码证据细节。同格式切歌无声（6c）已修复；进程内输出线程注册 MMCSS，重采样混叠压到 -125 dB 以下。一次约 50 秒、含暂停、恢复与切歌的端点 PCM 抓取中没有欠载、断音，也没有由本项目代码造成的跳变；削波来自音源本身。远程时钟与 EOS 的审计证据仍见 [AUDIO_CORRECTNESS_AUDIT_2026-11-16.md](AUDIO_CORRECTNESS_AUDIT_2026-11-16.md)。旧日志里的“稳定”只代表当时的设备、客户端和路径范围。

这份文件回答一个问题：**现在的 1.0.0 能不能算完成版？**

答案分两种口径，别混着说：

- **「在我这台机器、这个客户端版本、这个耳机上稳定用」→ 是。** 独占接管、切歌、
  拖进度、切端点、一键安装、托盘常驻、卸载，都有实测证据。
- **「可以发给任何人、插任何设备都能用」→ 不是。** 卡在下面 P0 第一条。

下面的清单按「影响面 × 修起来的代价」排序。P0 不解决，后面都只是自娱自乐。

### 5c. 暂停让出设备与自动共享（2026-11-25）

起因：独占时别的应用（浏览器视频、播放器）没有声音，暂停也一样。参考了 RateSync（macOS）的多播放器仲裁，
但 macOS 上它只改采样率、所有应用始终能出声；Windows 独占下设备同一时间只属于一个流，问题不一样。

先在 MOONDROP MM3A 上实测了会话层能看到什么（`mod/tools/sessprobe.c`，`bash mod/build.sh probe`）：

| 场景 | 结果 |
|---|---|
| 独占播放中，一个**从没出过声**的进程尝试共享输出 | 失败 DEVICE_IN_USE；但会先触发一次 OnSessionCreated |
| 独占播放中，一个**之前出过声**（会话还在）的进程再次尝试 | 失败，**没有任何通知**，会话状态不变 |
| 独占流 Stop 但未释放（即暂停） | 别的进程仍然 DEVICE_IN_USE：暂停占着设备 |
| 设备共享时 | Active 会话加峰值表能准确看出谁在出声 |
| 别的应用共享播放时抢独占 | 成功（「独占优先」默认开）；对方的流被作废，原因 ExclusiveModeOverride |

所以「独占时检测到别的应用想出声就让出」做不到可靠，改成：

- [x] `idle_release_ms`（面板「暂停时让出声卡」，默认不让出）：暂停够久就释放设备侧（独占流、闸门、audiohost 连接），
      客户端的流、环形缓冲、代理对象和时钟都保留；继续播放走现有的重建路径，时钟从暂停处接着走。
      暂停计时以 generation 为令牌，期间恢复播放或重建过设备都会作废这次计时
- [x] 收回前检查：重建设备侧前扫描该端点的会话（Active 且峰值 > -80 dBFS，排除自己、同名客户端进程、
      NexAudioHost 和系统声音）。没开自动共享时照样收回独占，但日志与面板提示「从 X 手里收回了声卡」
- [x] `auto_shared`（面板「别的应用出声时改走共享」，默认关闭）：建设备侧时（新流、让出后继续、暂停后继续）
      如果别的应用在出声、或 `share_quiet_ms`（默认 3 s）内出过声，就用客户端原格式开共享流
      （AUTOCONVERTPCM，由系统混音器转换），ENGAGED 标 `[shared]`、`output=shared`；
      之后在某次继续播放时，别的应用已经安静够久，就回到独占。曲中不切，避免断音
- [x] 定时轮询模式暂停后缓冲是满的时，设备永远不会再启动（共享流实测卡死）：恢复时带着队列里的数据直接启动，
      与事件模式一致
- [x] `nexsim` 新场景 `release`、`share` 和 `--quiet`（约 -70 dBFS）。设备上已有别的应用在出声时，
      需要安静设备的检查会跳过并注明原因
- [x] SMTC 实验脚本 `mod/tools/smtc_probe.ps1`：看浏览器在拿不到声卡时是否仍报「正在播放」。
      已知 Veyra Video Player 播放时 SMTC 里没有会话，所以 SMTC 只能覆盖接入它的应用
- [ ] 实机：在安静的设备上跑 `nexsim --quiet release share`（2026-11-25 跑时 Veyra 在放视频，
      两项都只验证了「共享流暂停后能继续」那一半）
- [ ] 实机：网易云独占播放时用浏览器放视频，跑 `smtc_probe.ps1`，看浏览器是否报 Playing；
      是的话，宿主可以用它作为「有人想出声」的信号，在独占时也能及时让出
- [ ] 曲中、同格式连续切歌时，共享流不会回到独占，要等到下一次暂停后继续、拖进度或换格式

### 6. 88.2 的转换策略

现在候选顺序是「源率 → 最近的更高 → 从高到低更低」，所以 88.2 源在只支持
44.1/48/96 的设备上会落到 **96 kHz**（160:147 有理数比，保带宽）。

另一个选择是优先整数比 → **44.1 kHz**（2:1 抽取，最省，但砍掉 22.05k 以上）。

- [x] 默认策略为 `bandwidth`
- [x] 配置开关 `src_prefer=bandwidth|simplicity`，面板可切换
- [x] 回归覆盖整数比候选排序

**这不是 bug，是取舍。** 现在默认「保带宽」，代价是一次非整数比重采样。

### 6c. 同格式切歌后偶尔无声，直到下一首换格式

**现象**：两首格式相同的歌连续播放（例如都是 44.1 kHz / 16 bit），切到第二首后没有声音、进度不走；直到下一首格式不同、重新建立输出才恢复。

**日志顺序**（2026-11-20 03:02，`sink.log`）：

1. 第二首到来时走同格式交接：`same-format client handoff kept generation 1`，`Start -> S_OK (same-format handoff joined running generation)`。
2. 约 1 秒后客户端调用 `Stop`，输出线程正停在 `GetBuffer`：`drain thread parked at stage 2 … generation 1 abandoned`。
3. 随后的 `Start` 失败：`Start -> no device generation`。这一首一直无声，到下一首格式变化时 `new client while owner idle … handing over` 才重建。

**范围**：新旧音频 DLL 都有。旧版日志中同格式交接 619 次，出现 8 次 `Start -> no device generation`；新版实测 5 首里出现 1 次。相关代码在 `mod/src/sink_lifecycle.inc`（放弃一代的分支）与 `mod/src/sink_hooks.inc`（`Start` 无代可用时的处理），AudioPolicy 与 nexui 的改动没有涉及。`mod/test/regression.c` 的生命周期压力测试偶发失败（1811、1814 行，约十次一次），可能是同一处竞态。

- [x] 用回归测试复现：同格式交接后 `Stop` 时输出线程卡在 `GetBuffer`，再 `Start`
- [x] 放弃一代之后，`Start` 能重建输出，而不是返回 `no device generation`（同时放弃期间时钟保持最后位置）
- [x] 查清并消除生命周期压力测试的偶发失败（同一缺陷；负载下 120 次、串行 50 次全部通过）

**验收**：连续切换同格式歌曲 50 次以上，没有无声段；压力测试连续运行 50 次全部通过。

## P2 · 功能缺口

### 7. 软件音量端点在独占下不可调

WASAPI 独占的固有限制。端点有硬件音量节点时系统音量条仍有效；纯软件音量的
端点（部分 HDMI、部分主板声卡）在独占下就是调不了。

**已决定不做模块侧数字衰减**（不拿比特换音量）。这是产品决策，不是待办。

### 8. 四条通路只做了一条

WASAPI 独占 ✅ ／ ASIO ❌ ／ OpenHome ❌ ／ DLNA ❌

面板原计划分「本机播放 / 网播播放」两个页签，本机页签里在 WASAPI 端点和
ASIO 驱动之间二选一。目前只有第一条。

2026-11-23 决定：ASIO、DLNA/UPnP、RAAT 这些新输出通路**先不做**，先把 WASAPI 这一条做扎实（见 5a、5b）。

### 9. 设置面板回归

`ui/panel.js` 已有 Node 契约检查和当前网易云 CDP 验收；浏览器交互覆盖仍需扩展。

- [x] 第一阶段 UI 结构改版：分组、状态摘要、原生行布局、严格原样联动
- [x] 面板状态与 `hook.cfg` 双向同步的验收（2026-11-20 真机：面板改缓冲帧数保存后 `hook.cfg` 同步且其他字段不变；外部改 `hook.cfg` 后重新打开设置窗口即显示新值；宿主默认值与音频策略一致，回归覆盖读写往返与非法值回退）

## 怎么判断「可以发了」

一份可执行的门槛，不是感觉：

1. 干净 Win11 虚拟机装完 10 分钟，exe 还在（Defender 不拦）
2. 三个不同客户端版本，两个不同声卡/耳机，都能出声且日志说清用了什么格式
3. 从零克隆 → `bash mod/build.sh test` 全 PASS → `bash release.sh` 出包，
   CI 上同样能跑通
4. README 里的「已知问题」没有一条会让人装完就懵

第 1 条是硬门槛，其余三条是质量线。
